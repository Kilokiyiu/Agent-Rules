# 06 · 测试验证（P1）

**简体中文** | [English](06-test-verification.md)

有改动就一定要验证，验证结果必须是真实运行的输出；测试失败不许以任何形式掩饰。

## 为什么需要这条

不约束时，AI 的典型行为链是：改完代码 → 说"应该没问题" → 结束。这句话里的"应该"意味着它可能没有进行有关测试。更危险的变体是：测试失败时，它选择删掉测试用例或跳过失败项，让结果看起来是可行的——项目表面上健康，实际上可能已经埋下了风险。

## 适用时机

每一次代码修改之后。修复 bug 时尤其要按"复现 → 根因 → 修复 → 验证"的顺序走，顺序本身比修复更重要——跳过复现直接改代码，修的经常不是真正的病因。

## 提示词（可直接使用）

```text
【测试验证】
1. 每次代码修改后必须运行构建/测试命令，并回传真实输出。
2. 项目没有测试时，至少做一次编译/语法/最小运行验证，并说明验证了什么、
   没验证什么。
3. 修复 bug 时：先复现 → 确认根因 → 修复 → 验证原场景不再复现。
   禁止跳过复现直接改代码。
4. 测试失败时如实报告失败输出，不得通过删测试、跳过测试让结果"变绿"。
```

## 典型违例信号

- "应该可以了""理论上没问题"——但没有附带任何运行输出
- 测试数量变少，或失败项从列表里消失了
- 修 bug 时说不出复现步骤，直接指向一个修改点

## 如何调节

- **没有测试基建的项目**：第 1 条降级为"编译通过 + 最小运行"，但第 4 条（不许拆保护网）任何项目都不能松
- **有 CI 的项目**：可以把"回传真实输出"升级为"必须等 CI 结果并附运行链接"
