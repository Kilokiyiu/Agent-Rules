# 05 · 计划先行（P1）

中大型改动先出计划方案、你确认后 AI 才动手；发现计划错了就停下来重新确认。

## 为什么需要这条

AI 拿到需求后的默认行为是直接开写，写到一半发现方向不对，然后在不告诉你的情况下悄悄改方向——你最后拿到的是一个"结果上可能对"但过程对你而言完全失控的改动。计划先行的本质是把"方向对不对"这个最贵的判断提前到成本最低的时刻。

## 适用时机

满足任一条件即触发：

- 涉及 3 个以上文件的改动
- 存在多种技术方案可选（架构、库、数据结构）
- 预计工作量较大或不可逆程度较高

## 提示词（可直接复制）

```text
【计划先行】
1. 涉及 3 个以上文件、或预计超过 30 分钟工作量、或方向存在多种选择的任务，
   必须先输出改动计划：文件清单 + 每处改什么 + 风险点，获得确认后再动手。
2. 计划获批后仍不得超范围执行；执行中发现计划有误，先停下说明新方案，
   重新确认。
3. 用户只给了目标没给方案时，先问关键决策点（技术选型/结构划分），
   不要替用户默默做架构决定。
```

## 典型违例信号

- 长篇执行过程你完全看不到中间决策点，最后直接甩出结果
- 中途换了方案但没提前跟你说明（代码里出现计划外的抽象层）
- 你说"做个 XX"，它直接选定了框架开始搭项目骨架

## 如何调节

- **开发早期 / 探索性实验**：可关闭本条，追求速度
- **重构期 / 接近成型的项目**：必须开启——这个阶段方向错误的返工成本最高
- 如果你习惯先自己规划架构（如先出 ASCII 图再动手），可以把本条改成"AI 收到计划后先复述理解、指出疑点，确认无误后再执行"
