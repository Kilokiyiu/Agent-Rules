# 11 · 文档写作（P1*）

[English](11-documentation-writing.md) | **简体中文**

> 日常按 P1；文档本身是主要产出时按 **P0**。速查表可豁免文风条款；治理条款不豁免。

> 用途：贴进 CLAUDE.md / AGENTS.md / 系统提示词，约束 AI 初步撰写项目文档时的文风。
> 背景：AI 写文档的默认病根是**写给"知道答案的人"看**——它把输出当记忆索引而非讲解，导致电报体、元语言堆砌、有结论无因果。本规则的每一条都在对治这个病根。

---

## 一、总原则

1. **读者画像**：读者可能是"3 个月后项目的作者本人 + 有可能时没参与过任何讨论的同事 + 也有可能是第一次接触项目的陌生人"。他不完全了解项目背景，也可能不记得任何一次对话中形成的缩写、比喻和暗号。凡是只在对话里出现过的词，文档里必须重新解释。
2. **文档是讲解，不是索引**：正文必须由完整句子构成，表格/列表是正文的补充而非替代。一篇只有表格和短语的文档是不合格的。
3. **先具体后抽象**：任何抽象原则都要先用一个本项目的具体场景垫底，再上升为原则。禁止无例子的抽象名词。

---

## 二、语言规则

| # | 规则 | 违例示例（禁止） | 正确示例 |
|---|------|----------------|---------|
| L1 | **禁止电报体**：正文句子必须有主语、谓语、连接词（因为/所以/比如/否则/这意味着） | "不作废决策史，不分 phase 施工表" | "文档不记录决策的历史演变（那段历史由 git 承担），也不按施工阶段拆分任务表，这样它才不会随开发推进而过期" |
| L2 | **术语三件套**：抽象名词（如"契约""边界""形状"）首次出现时必须给：① 一句大白话定义 ② 一个本项目具体例子 ③ 为什么要管它 | "契约：依赖日志里哪些字段？" | "契约指两个模块之间约定好的交接内容。例如 Parsers 依赖 JSONL 里的 `ts`、`op`、`bytes` 三个字段——只要这三个字段不变，C++ 采集侧怎么改都不影响 C# 分析侧。管住契约，两侧才能独立演进" |
| L3 | **因果成对**：每条规则/决策必须写"做了什么 + 为什么"，禁止只留结论 | "失败：坏数据早暴露，避免假阴性" | "失败策略：未知事件类型宁可抛异常也不静默跳过。因为静默跳过会让真实的泄漏记录漏检（假阴性），而误报的代价只是多看一眼日志" |
| L4 | **一句一概念**：一句话里最多出现一个未解释的新概念。出现两个时拆成两句 | "运行层之上练决策层，再抽象成产品拆法" | 见下方改写 |
| L5 | **自问自答开头**：每个章节用读者会问的真实问题引入，再给答案 | "三层，别混着学" | "为什么学架构要把运行、决策、产品分三层？因为混着学时，你会拿着源码层面的问题去问架构文档，两边都得不到答案" |
| L6 | **允许有益冗余**：关键结论允许在正文和表格/小结里重复出现一次。人阅读是线性的，重复不是浪费 | — | — |
| L7 | **比喻要注册**：自创比喻（如"翻译官""梯子"）首次出现时必须绑定到正式概念，后文统一使用 | — | "把 Parsers 比作'翻译官'：只负责把一行日志翻译成一个结构化事件，不做任何判断" |

### L4 改写示例

原句（违例）："运行层之上练决策层，再抽象成产品拆法。"

改写："这份课分两层往上走：第一层从'这行代码在干嘛'（运行层）上升到'为什么这样设计'（决策层）；第二层再把设计思路抽象成一套拆解新产品的通用步骤。"

## 三、结构规则

| # | 规则 | 说明 |
|---|------|------|
| S1 | **三问开场**：每篇文档开头回答——这是讲什么的？我什么时候需要读它？读完我能做什么？ | 可以是三行，但必须完整成句 |
| S2 | **阅读路径**：导航类文档必须按读者身份给顺序，不能只列文件清单 | "想用这个工具→A→B；想改它→C→D；想学东西→E 起步" |
| S3 | **禁止"见 xxx"作为唯一解释**：链接可以补充细节，但正文必须先自含最低限度的解释 | "见 module-map.html" 必须改为 "判断逻辑在分析器（详见模块地图）" |
| S4 | **决策摘要带为什么**：任何"摘要/速查/对照表"的每一条都隐含指向一个完整解释，正文里必须存在该解释 | 摘要可以是短语，但对应展开必须存在于同文档正文 |
| S5 | **章节标题禁止裸元词**："边界""形状""失败""替换"不能单独作标题，要带上场景 | "边界：为何只产出事件，绝不算泄漏？" ✔ / "边界" ✘ |

## 四、禁止清单（可直接贴进提示词）

- 禁止以单个抽象元词（边界/契约/形状/失败/替换/分层）作标题或正文而无一解释
- 禁止连续三行以上没有完整句子
- 禁止只有表格没有过渡句——表格前后必须各有一句完整的话说明它是什么、怎么读
- 禁止无人称命令句连发（"默写：输入/输出/分支种类"）
- 禁止把只在对话/备忘里出现过的缩写和暗号直接写进文档
- 禁止用"见链接"代替解释
- 禁止结论句不带原因独立成段

---

## 五、文档治理规则（写什么，不写什么）

> 这一节约束的是文档**内容策略**，与前面的文风规则互补。第 7 条配合项目级 agent 配置（CLAUDE.md / AGENTS.md / 插件权限）可做成硬性权限约束，不依赖 AI 自觉。

1. **只描述当前状态**：所有文档和代码注释只描述现存状态，不记录任何 AI 历史修改记录。
2. **未确认的规划不入档**：某次开发中临时规划的阶段（如 phase1~phase5）不得写成文档字段或业务规则——文档只按代码和项目现状更新，不预测尚未落地的规划。
3. **决策更替即清除旧迹**：若决策 A 是旧现状、决策 B 是本次新决策且 A 已作废，文档直接写 B，不保留"原来是 A"的任何痕迹。读者不应需要分辨"哪些是历史、哪些是现行"。
4. **文档描述架构而非实现**：实现细节以代码库为准，文档只给出"去哪找"的指引（入口文件、模块地图）。拿着文档去代码库能找到实现，反之不要求成立。
5. **文档不是更新记录表**：变更历史由 git 承担。文档忠实于现存架构，不做流水账。
6. **README 为唯一导航**：维护 `docs/README.md` 作为文档总导航，登记各文档路径与一句话说明；新增文档必须先登记，避免孤儿文件。
7. **文档写入权收归主代理**：代码实现的子代理不得直接修改文档库，只能提交修改建议；由主代理判断是否采纳，采纳后再派代理执行写入。

## 六、AI 交稿自检清单（要求 AI 在返回前逐项自检）

1. 遮住文中所有加粗短语和表格，只读正文——一个没有上下文的人能读懂吗？
2. 让一个"知道项目但没参与讨论"的人读第一段，他 30 秒内能说出这篇文档讲什么吗？
3. 文中每个新概念首次出现时，是否同时有定义、例子、理由？
4. 每个"摘要"条目在正文里是否有对应的完整解释？
5. 是否存在任何一句读者会问"这是在说什么"却没有答案的话？
6. 有没有连续 3 行以上没有完整句子？

任何一项不通过，AI 必须修改后重新交稿，不得带病交付。

## 七、提示词模板（直接复制使用）

```
请为项目【项目名】撰写【文档类型：入门教程/架构说明/使用指南/学习笔记】。

读者画像：了解本项目大方向，但没有参与过相关讨论，不记得任何对话中形成的
缩写、比喻和决策背景。三个月后的项目作者本人也在读者之列。

写作要求：
1. 正文一律用完整句子，包含主语谓语和连接词；禁止电报体短语充当正文。
2. 任何抽象概念首次出现时，按"大白话定义 → 本项目具体例子 → 为什么重要"
   三步引入；一句话最多引入一个新概念。
3. 每条规则或决策必须同时给出"做了什么"和"为什么"，禁止只写结论。
4. 每个章节开头用一个读者会问的真实问题引入，再展开答案。
5. 表格和列表前后必须各有一句完整的话交代上下文；关键结论允许在正文与
   表格中重复一次。
6. 导航类内容必须按读者身份给出阅读顺序，不能只列文件清单。

内容治理要求：
1. 文档与代码注释只描述当前状态，不记录任何历史修改过程或 AI 操作记录。
2. 未确认的实现规划（如临时划分的 phase1~5）不得写进文档；只按代码与
   项目现状更新。
3. 决策被新决策取代时，直接写新决策并删除旧决策的全部表述，不保留
   "原来是 X、现在改成 Y"的痕迹。
4. 文档描述架构而非实现：实现细节以代码库为准，文档只给出查找指引。
5. 不把文档当更新记录表，变更历史由 git 承担。
6. 若本次涉及 docs/README.md 导航范围（新增/改名/删除文档），必须同步
   更新导航表。

禁止事项：
- 单个抽象元词（边界/契约/形状/失败等）直接作标题或正文
- 连续三行以上没有完整句子
- 用"见 xxx 链接"代替解释
- 无解释地使用只在对话中出现过的暗号、缩写、比喻

交稿前自检：
按以下清单逐项检查，任何一项不通过必须修改后重新交稿——
□ 只读正文（忽略加粗和表格）能读懂
□ 第一段 30 秒内可判断文档主题
□ 每个新概念有定义、例子、理由
□ 每个摘要条目在正文中有完整对应解释
□ 没有连续三行无完整句子
□ 文档中没有残留已作废决策、未确认的 phase 规划或历史修改记录
□ 涉及文档增删时，docs/README.md 导航表已同步
```

## 附：为什么这套规则有效

AI 文档难读的本质不是"写得差"，而是**写作目标错位**：AI 把"信息密度最大化"当成了目标，因为训练语料里高分文档（速查表、release notes、设计备忘）确实全是电报体。但这些文档的读者是"刚开完会的人"，而你需要的读者是"三个月后的人"或者“陌生人”。

人写的教程之所以好读，是因为作者每写一句都在心里模拟读者发问："这话你看得懂吗？为什么？举个例子呢？"——这个模拟过程就是本规则试图强制 AI 执行的东西。

使用建议：规则不必全贴。日常小文档贴"七、提示词模板"即可；给 AI 配置项目级规则（CLAUDE.md/AGENTS.md）时贴全部，其中第五节治理规则的第 7 条应同步配置为硬性权限（禁止子代理写文档库）。
